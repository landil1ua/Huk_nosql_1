# README
## PART 1
### Питання 1. Чому аудіо-характеристики винесені в окремий об’єкт `audio_features`, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?

> **Відповідь:**
> Ми винесли їх в окремий об'єкт `audio_features`, щоб красиво згрупувати купу однотипних полів в одному місці. Це банально покращує читабельність документа. До того ж, це дуже зручно на практиці: коли нам потрібно передати ці метрики далі — наприклад, в ML-модель або аналітичний pipeline — ми просто забираємо весь об'єкт цілком.
>
> * **Коли це вигідно:** Коли ці характеристики логічно пов'язані між собою і майже завжди використовуються разом як єдине ціле.
> * **Коли це створює проблеми:** Якщо нам потрібно часто робити запити по окремих полях або незалежно їх індексувати. Постійно прописувати точкову нотацію (на кшталт `audio_features.danceability`) у складних запитах — це зайвий головний біль, і підтримувати таку схему стає важче, ніж звичайну плоску структуру.

---

### Питання 2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?

> **Відповідь:**
> Тут усе просто: у одного треку часто буває кілька виконавців (фіти, колаборації). Якщо запихати їх в один рядок, то для банального додавання чи видалення артиста довелося б кодити складну й багомістку логіку обробки рядків.
>
> Масив повністю вирішує цю проблему, бо MongoDB «з коробки» вміє круто працювати з масивами. Наприклад, простий запит `{ artists: "Drake" }` автоматично пройдеться по всьому масиву і знайде всі треки, де є Drake, навіть якщо він там не один.
>
> Якби ми зберігали це рядком (наприклад, *"Drake; Future"*), нам довелося б ліпити регулярні вирази через `$regex`. А це мало того, що повільно і б'є по перформансу, так ще й ненадійно. Крім того, завдяки масиву ми можемо з легкістю використовувати потужні оператори агрегації на кшталт `$elemMatch`, `$size` (щоб відфільтрувати треки за кількістю артистів) або `$unwind` (для зручної аналітики щодо кожного виконавця окремо).

### Питання 3. Що таке `$out` і чим він відрізняється від `$merge`? Коли використовувати кожен?

> **Відповідь:**
> Обидва оператори потрібні для збереження результатів агрегації, але працюють вони абсолютно по-різному:
>
> * **`$out`** діє радикально — він бере і повністю перетирає цільову колекцію новими даними. Ця операція є атомарною: тобто або все успішно заміниться, або (якщо щось пішло не так) стара колекція залишиться недоторканою. Його варто використовувати, коли потрібно з нуля перебудувати всю колекцію (як у нашому випадку з трансформацією `tracks_raw` → `tracks`).
> * **`$merge`** працює гнучко — він акуратно об'єднує результати з тим, що вже є в базі. Залежно від параметрів (`whenMatched` / `whenNotMatched`), він може додати нові документи, оновити старі або просто пропустити дублікати. Його ми використовуємо для точкових апдейтів, коли треба оновити лише шматок даних, не чіпаючи все інше.

## PART 2
### Питання 1. Для чого використовується інструкція `$unwind`?

> **Відповідь:**
> Якщо коротко, `$unwind` використовується для того, щоб «розгорнути» масив у документі. Коли у нас в одному полі лежить масив із кількома елементами, `$unwind` розбиває цей один документ на кілька окремих — по одному документу на кожен елемент масиву. При цьому всі інші поля вихідного документа просто дублюються.
>
> На практиці це найчастіше потрібно для аналітики та агрегації. Наприклад, якщо у нас є трек, де в масиві `artists` записано три артиста, то після `$unwind` ми отримаємо три ідентичні треки, але в кожного в полі `artists` буде вже по одному конкретному імені. Тепер ми можемо легко згрупувати дані через `$group`, порахувати середні метрики або кількість треків для кожного виконавця окремо. Без цього оператора робити аналітику всередині масивів дуже незручно.

---

### Питання 2. Чим `$stdDevPop` відрізняється від `$stdDevSamp`?

> **Відповідь:**
> Обидва оператори рахують середньоквадратичне відхилення (яке показує, наскільки сильно наші дані розкидані навколо середнього значення), але вони використовують різні формули залежно від того, з яким обсягом даних ми працюємо:
>
> * **`$stdDevPop` (Population)** — рахує відхилення для **генеральної сукупності**. Тобто його ми беремо тоді, коли в нас на руках є абсолютно всі можливі дані. Наприклад, якщо ми хочемо порахувати точне відхилення тривалості взагалі всіх треків, які є в нашій базі. Формула ділить суму квадратів відхилень на загальну кількість елементів $N$.
> * **`$stdDevSamp` (Sample)** — рахує відхилення для **вибірки**. Його використовують, коли ми маємо лише якусь обмежену частину даних (наприклад, випадкові 500 треків), але на основі них хочемо оцінити загальну картину. Оскільки вибірка ніколи не є ідеальною, в її формулі використовується корекція Бесселя — ділення йде не на кількість елементів, а на $n - 1$. Це трохи збільшує підсумкове відхилення, компенсуючи потенційну похибку вибірки.

## PART 3
### Питання 1. У запиті 1 ми фільтруємо виконавців, у яких менше 5 треків. Як зміниться результат, якщо знизити поріг до 1? А що станеться, якщо вибирати виконавців із більш ніж 50 треками? Поясніть результат.

> **Відповідь:**
> При зниженні порогу до 1 трека до вибірки потраплять виконавці з єдиним треком — так звані «однохіти». Якщо цей трек випадково отримав високу популярність (наприклад, завірусився), такий виконавець може опинитися у топі, хоча насправді він не є стабільно популярним артистом. Це спотворює рейтинг. При підвищенні порогу до 50+ треків залишаться лише дуже плідні виконавці з великим каталогом — наприклад, Metallica або Nirvana. Їх буде небагато, але це справді стабільно популярні артисти з підтвердженою аудиторією.

### Питання 2. У запиті 3 ми фільтруємо жанри з менше ніж 100 треками. Чи зміниться результат, якщо знизити поріг до 50? Поясніть результат.

> **Відповідь:**
> Датасет збалансований: кожен жанр містить рівно 1000 треків — це характерно для синтетичних навчальних датасетів з Kaggle, де дані вирівнюють по категоріях для коректного навчання моделей. Через це зниження порогу з 900 до 50 ніяк не вплине на результат — всі жанри однаково проходять будь-який поріг до 1000. Результат зміниться лише якщо поставити поріг понад 1000 — тоді жоден жанр не пройде фільтр і отримаємо порожній результат.

## PART 4
### Питання 1. Що змінилося в плані виконання?

> **Відповідь:**
> До індексу MongoDB використовував повне сканування колекції (SORT → COLLSCAN під капотом) і переглянув усі 113 999 документів. Після створення складеного індексу { track_genre, popularity, audio_features.danceability } план змінився на FETCH — MongoDB спочатку знайшов потрібні записи через індекс, а потім забрав лише їх. Кількість переглянутих документів скоротилася з 113 999 до 354, тобто у 322 рази. Окремий крок сортування зник, бо дані в індексі вже впорядковані за popularity.

### Питання 2. Як зрозуміти, що індекс використовується? Наведіть скріншот або значення полів із explain(), які це підтверджують.

> **Відповідь:**
> Два ключових поля з виводу explain("executionStats"):
queryPlanner.winningPlan.stage — якщо значення IXSCAN, FETCH або PROJECTION_COVERED, індекс використовується. Якщо COLLSCAN — індексу немає або MongoDB вирішив його не використовувати.
executionStats.totalDocsExamined — з індексом це число близьке до кількості результатів. Без індексу — дорівнює розміру всієї колекції (113 999).
Результати, що підтверджують використання індексу: /results/part4_results.txt

### Питання 3. Чи є цей запит покривним (covered query)? Надайте розгорнуту та обґрунтовану відповідь у файлі README.

> **Відповідь:**
> Запит без проєкції — не покривний. Stage FETCH, docs examined 317 — MongoDB знайшов документи через індекс, але потім пішов на диск за повним документом, бо не знав які поля потрібні.
Запит з явною проєкцією { track_genre: 1, popularity: 1, _id: 0 } — покривний. Stage PROJECTION_COVERED, docs examined 0. Усі поля фільтру і проєкції є в індексі { track_genre, popularity, audio_features.danceability }, тому MongoDB отримав відповідь повністю з індексу, не звертаючись до жодного документа колекції. Ключова умова covered query: поля фільтру + поля проєкції ⊆ поля індексу, і _id виключений явно.

## Налаштування оточення

### Вимоги
- Python 3.x
- mongosh
- Акаунт MongoDB Atlas (безкоштовний тір M0)

### Встановлення

1. Клонувати репозиторій:
```bash
git clone https://github.com/landil1ua/Huk_nosql_1.git
```

2. Створити та активувати віртуальне середовище:
```bash
python -m venv venv
.\venv\Scripts\Activate.ps1
```

3. Встановити залежності:
```bash
pip install -r requirements.txt
```

4. Налаштувати підключення до MongoDB Atlas:
- Створити файл `.env` у корені проекту з наступним вмістом:
```MONGO_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/
```

5. Покласти датасет у папку `data/`:
- Завантажити [Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset) з Kaggle
- Зберегти як `data/dataset.csv`

### Запуск

```bash
# Частина 1 — завантаження та трансформація
python scripts/01_load_data.py
mongosh "URI" --file scripts/02_transform.js

# Частина 2 — запити
mongosh "URI" --file queries/part2_queries.js

# Частина 3 — аналітика
mongosh "URI" --file queries/part3_aggregations.js

# Частина 4 — індекси
mongosh "URI" --file queries/part4_indexes.js
```
